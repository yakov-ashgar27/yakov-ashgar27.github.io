Fitness & Nutrition Tracking System

A case study in taking a product idea from user needs to a complete system design: requirements, architecture, data model and the trade-offs in between.

Year
2024
My role
Lead – planning & design
Scope
End-to-end
Focus
Systems analysis

the idea

The problem

People who train and watch their nutrition usually track workouts in one place, meals in another, and progress in their head. The data exists, but it is scattered, so it is hard to see what is actually working.

The goal

  • One system for logging workouts and meals
  • Clear, automatic view of progress over time
  • Personal goals the system can measure against
  • A structure that stays fast as data grows

process

Requirements

Defined user needs and operational requirements before any design.

Analysis

Mapped user flows and the information each screen needs.

Architecture

Split the system into interface, processing and data layers.

Data design

Built the data structure and the flow between modules.

Gap analysis

Checked the design against technical constraints and performance needs.

system architecture

The system is built in three layers, so each part has one job and data moves in a predictable direction.

key insights

Requirements first saves rework

Defining what users and operations actually need before designing meant the architecture answered real questions instead of guessed ones.

The data model drives everything

Once the entities and relationships were right, the screens and the processing logic followed naturally from them.

Constraints are design inputs

The gap analysis showed that performance limits should shape the design early, not be patched in at the end.

Clear layers, clear ownership

Separating interface, logic and data makes each part easier to reason about, test and change on its own.
